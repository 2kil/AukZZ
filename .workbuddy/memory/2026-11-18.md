## 修复 `audiocpp_cli` 退出崩溃 0xC0000005（3221225477）

**现象**：带 `--voice-ref` 的零样本请求，WAV 写完后进程以 3221225477 退出；Instruct（无参考音频）退出码恒为 0。

**排查路径（按排除法）**
1. 换官方 `cudart-windows-x64-cuda12.4.zip` 的 4 个 DLL（cudart64_12/cublas64_12/cublasLt64_12/cufft64_11）→ 仍崩，排除 CUDA 版本错配。
2. 换 Vulkan 后端 → 同样段错误，且产物字节数与 CUDA 完全一致（96044），排除 GPU 后端。
3. `--threads 1` 首次 exit=0，再测又崩 → 间歇性，是竞态而非线程数阈值。
4. Instruct 路径（不走重采样）连续 3 次 exit=0 → 锁定**参考音频重采样路径 = libsoxr**。

**根因**：之前用 TDM-GCC(mingw-w64, msvcrt) 自编的 `libsoxr.dll` 与 MSVC(UCRT) 宿主进程混用 CRT，堆在退出阶段损坏。

**修复**：换成 MSYS2 **UCRT** 构建 `mingw-w64-ucrt-x86_64-libsoxr-0.1.3-6` + 其依赖 `libgomp-1.dll`（`mingw-w64-ucrt-x86_64-libgomp-16.2.0-7`），解包出 `ucrt64/bin/libsoxr.dll`、`libgomp-1.dll` 放到 `vendor/audio.cpp-cu124/`。压测 5/5 exit=0，产物字节数与修复前一致（同一音频）。

**顺带改进**
- `SynthesisResult` 增加 `notes` 字段：截断参考音频等**信息性提示**走 `X-Notes`，只有真问题才进 `X-Warning`
- WebUI 用灰色 `.noteline` 展示 notes、琥珀色 `.warnline` 展示 warning
- `gguf_preflight()` 把 `libsoxr.dll` / `libgomp-1.dll` 纳入必需项检查
- 保留「产物有效即成功」的兜底逻辑（现在正常情况下不再触发）

**注意**：`rm data/outputs/s*.wav` 会误删 `sample_*.wav`，清理时用精确文件名。

## 逐句语气合成（`POST /speech/segments`）

**结论先行**：AuK 没有「单次调用 + 每句不同语气」的原生能力（一次调用只有全局 `instruct`）。已实现分段方案：同一参考音色逐句生成，再逐句套语气，最后拼接。

**两种实现方式（`tone_mode`）**
- `edit`（默认，推荐）：零样本 TTS（Flash）+ 情绪编辑（Base），每句 2 次推理
- `prompt`：把语气写进生成指令 `Say the following with the same voice, in a {tone} tone: "..."`，每句 1 次推理，效果明显更弱
- `none`：忽略语气

**关键实测结论（重要）**
1. **Flash 不适合做编辑**：官方英文样例 emotion edit，Flash 的 happy/sad 谱质心只差 68Hz（1300 vs 1232），Base 差 173Hz（1428 vs 1255），耗时相近（8–10s）。因此新增 `GGUF_EDIT_VARIANT=base`，`/edit` 与分段的情绪步默认走 Base；缺 `auk-base-q8_0.gguf`（1.64GB）时自动回退 Flash 并给出 warning。
2. **情绪差异体现在频谱亮度，不在 f0**：f0 中位数几乎不动（258→265/264/273），但谱质心与 3kHz 以上能量占比明确变化。做效果验证必须看质心/HF 占比，不能用单一 f0。
3. 三句实测（calm/happy/sad）：质心 1359/1452/1390Hz、f0 249/282/261Hz —— 方向正确但幅度温和；三句 RMS 均 0.0680（`join_wavs` 的 RMS 对齐生效）。
4. `speak` 里塞语气词（prompt 模式）不可靠：happy 276Hz vs sad 264Hz 几乎无差别。

**实现**
- `audio.py::join_wavs()`：逐句读入 → 可选 RMS 对齐（限 ±6dB）→ 15ms 淡入淡出防爆音 → 按 `gap_seconds` 插入静音 → 返回 wav + 每句 start/end
- `audio.py` 新增 `probe_wav_bytes()`（内存 WAV 解析）、`_parse_riff_bytes()`
- `engine.py`：`_base_cmd(task, variant)` 支持逐次覆盖变体；`synthesize_segments()`（GGUF/Mock/Python 三引擎均有）；`_edit_variant_or_self()` 处理 Base 缺失回退
- `main.py`：`SegmentItem`/`SegmentsRequest` 模型 + `/speech/segments`，响应头 `X-Segments`、`X-Segment-Offsets`（`0.00-1.76|2.16-4.90|...`）、`X-Tone-Mode`
- WebUI：全宽「逐句语气合成」卡片，脚本格式「文本 | 语气」，含偏移表与播放器

**实测耗时**：3 句 edit 模式 42s；2 句 prompt 模式 12s。

**角色库现状**：15 个内置（用户新增 徐志胜 16kHz、潘雪柔被换成 44.1kHz 立体声 9.23s）；WAV 解析对 16k/24k/44.1k、单/双声道、PCM/float 全部一致。

## 整句情绪（`/speech` 的 `emotion` 参数）

**需求**：给参考音频做零样本克隆，同时指定整句情绪。

**结论**：AuK 没有「参考音色 + 情绪」的单次原生能力。试过两条路，最终选**指令注入 + 升级 Base**：

| 方案 | 做法 | 耗时 | 效果（谱质心 Δ vs 中性） |
|---|---|---|---|
| 两段式 | Flash 零样本 → Base 情绪编辑 | ~14s | happy +? / sad +? 基本无分离（1527/1548） |
| **指令注入（采用）** | 指令改成 `Say the following with the same voice, in a {emotion} tone: "..."`，并把该次调用从 Flash 升到 Base | **7–9s** | angry **+504Hz**、happy **+107Hz**、sad **−64Hz** |

**实现要点**
- `AukGgufEngine.synthesize(..., emotion=)`：情绪拼进 zero-shot 模板；`use_variant = _resolve_edit_variant(...)` 用 Base（缺 `auk-base-q8_0.gguf` 时回退 Flash 并 warning）；`num_inference_steps/guidance_scale` 判定改用 `use_variant`
- 无参考音频（Instruct TTS）也支持：情绪追加到 `voice_description`（中文用「，语气：X」，英文用「. Tone: X」）
- `mode` 返回 `zero_shot_tts+emotion` / `instruct_tts+emotion`，`X-Notes` 说明情绪注入方式与所用变体
- `MockEngine` / `AukEngine` 同步（Mock 记 warning、Python 栈同样拼指令）
- WebUI 合成卡片增加「整句情绪」下拉（8 个情绪词）

**重要经验**：情绪强度**不对称** —— 提升型（angry/happy）明显，降低型（sad）幅度小；`angry` 最容易做出差异（高频占比 0.249 vs 0.173）。验证情绪必须看**谱质心/高频占比**，f0 单独用会误判。

## 长文本自动分段合成（解决 20 秒上限导致的语速变快）

**问题**：`estimate_seconds` 算出的时长被 `min(…, MAX_GEN_SECONDS=20)` 截断，135 字文本（自然需 28 秒）被塞进 20 秒 → 实测语速 6.75 字/秒（正常 4.8）。

**实现**
- `config.py`：新增 `MAX_CHUNK_SECONDS`(默认 15)、`CHUNK_GAP_SCALE`(默认 1.0)
- `audio.py`：
  - `split_text()`：段落 → 句子（。！？!?…）→ 从句（，、；：）→ 硬切；贪心打包，每块 ≤ `max_seconds` 且 ≤ `max_chars`；英文硬切优先取词边界，并按语言区分字符预算（中文 4.6、英文 13 字/秒）
  - `pause_after()`：按块尾标点决定停顿（。！？ 0.45s、；：0.3s、，、 0.18s、无 0.25s）
  - `join_audio()`：拼接前**裁剪每块首尾静音**（阈值 3% 峰值、留 20ms），再按停顿插入静音、15ms 淡入淡出、±6dB 内 RMS 对齐 —— 不加裁剪时拼接处会出现 ~0.9s 空档
  - 重新加回 `probe_wav_bytes()`（内存 WAV 解析）
- `engine.py`：`AukGgufEngine.synthesize(..., max_chunk_seconds=None)` 入口判断：未显式给 `gen_seconds` 且估算 > 上限 → 走 `_synthesize_chunked()`；逐块用各自估算时长合成（种子逐块 +1），最后拼接；`mode` 变为 `zero_shot_tts+chunked`
- `main.py`：`SpeechRequest.max_chunk_seconds`(5–20s) 可覆盖默认；`X-Notes` 说明分了几块

**实测（135 字同一文本）**
| 指标 | 分段前 | 分段后 |
|---|---|---|
| 输出时长 | 20.00s（被截断） | 27.90s |
| 语速 | 6.75 字/秒（快 41%） | **4.84 字/秒**（自然） |
| 峰值/削波 | — | 0.508，无削波 |
| 请求耗时（CLI 模式） | 7.9s | 18.6s（3 块 × ~6.2s） |

短文本（24 字）不受影响：`mode=zero_shot_tts`，4.38s / 5.48 字/秒。

**注意**：CLI 模式下分段会成倍放大固定开销（每块 6-7s），要上直播必须配合常驻 `audiocpp_server`（每块 ~0.3s），否则长文本 3 块要 19 秒。

## 修复三处输出问题（数字时长、描述被朗读、英文提示）

**1. 数字被挤压（根因：估算器不数数字）**
- `audio.py::estimate_seconds()` 原来只用 `CJK_RE`/`WORD_RE`，**数字、%、单位字母一个都不计**：`现在下单只要199元` 按 7 汉字算 1.52s，"一百九十九" 白送 → 严重加速
- 新增 `spoken_seconds_of_numbers()`：每个数字组按 `max(2, 位数*1.3)` 音节、小数点 +1、"百分之" +3 音节（0.66s）
- 新增 `normalize_text()`：`90%`→`百分之90`、`10.8s`→`10.8秒`、`kg/ml/℃/min/h` 转中文单位，并删除汉字/数字之间的多余空格（用户反馈"前后加空格读出来异常"）
- 效果：`199元` 1.52→2.38s、`30%` 0.50→2.32s、`10.8s` 0.96→1.86s、`7.5折` 0.56→1.36s

**2. 音色描述被朗读（概率性）**
- 根因：模板 `请基于下面的描述: "{desc}",生成语音内容"{text}"`，描述里出现引号/换行会破坏结构，长描述也容易被"续读"
- 新增 `clean_description()`：剥离 `" ' “ ” ‘ ’ 「 」`、换行折空格、压缩空白、**超过 80 字截断**并加中文提示
- 新增泄漏检测：`instruct_tts` 且输出时长 > max(2.2×估算, 估算+2s) → 中文警告，提示缩短描述或改用角色
- 验证：`一位"温柔"的女声` 清洗为 `一位温柔的女声`，5 字文本输出 1.0s（正常）

**3. 英文提示改中文 + 移到底部日志**
- 引擎所有 notes/warnings 改中文（分段、参考截断、预算超限、teardown 崩溃、变体回退、降级模式）
- WebUI 删除 `#resNote` / `#editNote` 两个提示条，`X-Notes` 改为写入日志区：`提示：长文本已切分为 2 段（每段 ≤ 15 秒）以保证语速自然`

**回归**：smoke 7 项 PASS；UI 0 console 错误，日志正常输出中文提示。

**注意**：切换到常驻 `audiocpp_server` 后，`normalize_text()` / `clean_description()` 仍需在 Python 层先执行再转发，否则这两类问题会回来。

## 修复常驻模式下的 `requires Soxr HQ resampling`（间歇性 500）

**现象**：切常驻后偶发 `常驻服务合成失败（HTTP 500）：AuK audio conditioning requires Soxr HQ resampling`，重启后又能用。

**定位过程**
- CLI 目录里 `libsoxr.dll` / `libgomp-1.dll` 都在；进程模块列表确认已加载（`Get-Process audiocpp_server).Modules`）
- 实测：**24kHz 参考音频也需要 soxr**（首个 24k 音色请求后 soxr 才被 LoadLibrary 加载）
- 全新进程连续三次测试：两次首个音色请求成功（4.2s，之后 0.26s），一次失败 → **间歇性**
- 结论：soxr 是**懒加载**，首次 `LoadLibrary` 在 Windows 上偶发失败（杀软扫描/文件瞬时占用），失败表现为“看起来永久”的 500

**修复（三层）**
1. `AukServerEngine._request()`：识别 500 且消息含 soxr/resampling → 0.8s 后重试，最多 3 次；连续失败抛 `EngineUnavailable`(503)，消息里指明检查 `libsoxr.dll`/`libgomp-1.dll`
2. `audioserver.warmup()`：同样重试 3 次（启动预热不再可能因一次性失败而留下坏状态）
3. `_request()` 捕获 `ConnectionError` → 若允许自启则 `ensure()` 重新拉起并重试，实现**进程级自愈**（实测 kill 后首个请求 10.4s 返回 200）
4. `/health` 的 engine 段新增 `soxr_dll` / `gomp_dll` 布尔值，便于快速判断环境

**验证**：连续 5 次音色请求 200（首 0.84s，之后 0.26s）；kill 常驻进程后自动恢复；smoke 7 项 PASS。

## 严重问题：常驻服务返回参考音频（soxr 失败时的静默降级）

**现象**：用户报「生成的音频还是参考音频」。日志显示音色预热 3 次 500（soxr），但随后 /speech 返回 200，音频其实是参考音频。

**根因**：`audiocpp_server` 在 soxr 未初始化时，**不报错而是把 prompt（参考音频）当输出返回**；我们的引擎只校验 HTTP 200 与 WAV 合法性，因此毫无察觉。之前的重试只覆盖 500，覆盖不到这个“200 + 错误内容”的降级。

**修复**
1. `audio.py::similarity(a,b)` + `decode_mono()`：波形相关系数（不同采样率先线性重采样到同一率）
2. `AukServerEngine._guard_echo()`：音色请求返回后与 `voice-library/<name>.wav` 比对，相似度 ≥ 0.85 判定为回显 → `_recover()` 重启常驻进程 → 重试一次；仍 ≥0.85 则抛 `EngineUnavailable`(503) 并提示检查 soxr DLL
3. `_recover()`：仅当常驻进程由本服务拉起时重启（否则提示手动重启）
4. 预热日志修正：`warmup()` 改为返回 `(ok, elapsed)`，不再把失败记成“完成”；音色预热失败会自动重启进程重试一次
5. FastAPI `on_event` → `lifespan`（消除 DeprecationWarning）
6. `/sw.js` 返回 204（消除浏览器探测产生的 404 噪音）

**踩坑**：插入 `_guard_echo` 时用了 `def _synthesize_chunked` 作锚点，结果两次都命中 `AukGgufEngine` 的同名方法（应限定在 `class AukServerEngine` 之后），还误删了半截方法留下不可达代码。教训：跨类插入必须先用类起始行定位。

**验证**：启动日志干净（双预热均成功）；连续 3 次合成 200、3.00s、与参考相似度 -0.052；桩测试确认「参考音频回显」被抓（相似度 1.00 → 触发自愈）；正常音频不误判；smoke 7 项 PASS。

## 真正的根因：libwinpthread-1.dll 缺失（此前误判为“间歇性懒加载”）

**反证**：用户日志显示重启常驻进程两次后 soxr 仍 500 —— 如果是懒加载竞态，重启后必有一次成功。

**决定性诊断（静态，不启动服务）**
```python
ctypes.WinDLL(r'.\.venv\..\vendor\audio.cpp-cu124\libsoxr.dll')  # 加载失败
objdump -p libsoxr.dll  -> 依赖 libgomp-1.dll + api-ms-win-crt-*
objdump -p libgomp-1.dll -> 依赖 libwinpthread-1.dll   ← 该文件不在目录里
```
即依赖链 `libsoxr -> libgomp-1 -> libwinpthread-1` 断了最后一环。8 月/11-18 早上还是好的（当时 CLI 5/5 exit=0），后来该 DLL 从目录消失（很可能被杀软清理，或某次清理命令误删）。

**修复**
1. 从 MSYS2 UCRT 仓库取 `mingw-w64-ucrt-x86_64-libwinpthread-git-12.0.0.r747.g1a99f8514-1-any.pkg.tar.zst`，用 zstandard+tarfile 解包出 `libwinpthread-1.dll`(63,675B)，放入 `vendor/audio.cpp-cu124/` 与 `vendor/soxr-ucrt/`
2. `engine.py::soxr_chain_report()`：用 ctypes 真实 LoadLibrary（含 os.add_dll_directory）验证整条链，返回 `present/deps/loadable/error`
3. `gguf_preflight()` 必需项加入 `libwinpthread-1.dll`，且 `soxr.loadable=False` 时写进 `missing`（`/health` 直接可读）
4. `AukServerEngine.status()` 增加 `winpthread_dll` / `soxr_loadable`
5. `requirements.txt` 部署说明改成三件套 + MSYS2 下载链接

**验证**
- ctypes 加载成功
- CLI 参考音频路径连跑 2 次 exit=0
- 临时拉起常驻服务：预热 Instruct ok=3.36s、音色 ok=0.84s；2 次请求 200、2.50s、与参考相似度 -0.032（非回显）
- `gguf_preflight('flash')` ready=True, missing=[]

**经验**：`requires Soxr HQ resampling` 这个报错既可能是“DLL 缺失”也可能是“DLL 依赖缺失”，必须先 `objdump -p` 逐层查依赖，再用 ctypes 实测加载，不要凭“重启后有时能好”就下结论为竞态。诊断这类问题不需要启动服务。

## 「生成内容还是参考音频拼凑」的真实原因：零样本路径漏了 AuK 指令模板

**诊断方法**：用 CLI 路径（已验证正确的零样本）生成同文本/同种子基准音频，再与常驻服务输出做波形相关 + 谱质心/f0/rms 对比。A/B 三种传参：

| 服务端 input 形式 | 与 CLI 基准相关 | 谱质心 | f0 | 结论 |
|---|---|---|---|---|
| `今天天气非常好，我们出去走走吧。`（裸文本 + voice） | **0.088** | 1632Hz | 255Hz | 错：模型把句子当指令 |
| `Say the following with the same voice: "…"` | **1.000** | 1714Hz | 267Hz | 正确，与 CLI 逐字节同级 |
| `请用相同的音色说出下面这句话："…"` | 0.019 | — | — | 中文指令无效 |

**instruct 路径对照**（无参考音频）：服务端 `input=裸文本 + options.instruct` 与 CLI 基准相关 **1.000**，说明服务端自己会套描述模板，**不需要**外层包装；手动套 `请基于下面的描述…` 反而变成 0.116。

**根因**：`audiocpp_server` 把 `input` 原样当作 `--text` 转发，而 AuK 是指令跟随模型——零样本必须给完整指令 "Say the following with the same voice: ..."。CLI 引擎里我们自己做了 `ZERO_SHOT_TEMPLATE.format()`，`AukServerEngine._request()` 迁移时漏掉了这一步，于是模型把台词当指令，输出与文本无关，听感就是"参考音频拼凑"（但相似度仅 -0.05，所以 `_guard_echo` 检测不到，这解释了为什么防护没报错）。

**修复**：`_request()` 增加 `body_text = ZERO_SHOT_TEMPLATE.format(text=text) if voice else text`；仅零样本分支包装，instruct 分支保持裸文本。

**验证**
- `/speech` 安若柔同参数 vs CLI 基准：相关 **1.000**，3.00s
- 龙安欢 20 字：4.38s（4.57 字/秒），与参考相似度 +0.001
- 长文本 90 字：`zero_shot_tts+chunked`，18.50s，4.86 字/秒，1.49s 完成
- instruct 路径：相关 1.000（未受影响）
- smoke 8 项 PASS；新增 `tests/test_payload.py`（6 项，离线断言 payload，不依赖服务）

**教训**：迁移引擎实现时必须逐条对齐“文本是否被包装成指令”，这类差异不会报错、也不会被回显检测抓到，只能靠与已知正确实现的波形比对发现。以后新增引擎，先跑一次「同文本 vs CLI 基准相关度」作为验收。
